# AGENTS.md

## Область действия

Эти правила действуют для всего каталога `Assets/`. Это Unity-шаблон, поэтому изменения должны оставаться переиспользуемыми и не содержать логики, данных или брендинга конкретной игры без прямого запроса.

## Контекст проекта

- Версия редактора: Unity `6000.0.26f1` (Unity 6).
- Рендеринг: Universal Render Pipeline 17.
- Основной код проекта: `Source/Scripts/`.
- Основные сцены: `Scenes/BootsTrap.unity`, `Scenes/Menu.unity`, `Scenes/Game.unity`, `Scenes/Gym/Gym.unity`.
- Внедрение зависимостей выполняется через Zenject; регистрации находятся в `Source/Scripts/DI/Installers/`, сервисы — в `Source/Scripts/DI/Services/`.
- В проекте также используются UniTask, R3, DOTween, Newtonsoft.Json, Input System и Lean Localization. Не добавляй новую библиотеку, если существующая уже решает задачу.

## Организация изменений

- Новый игровой код помещай в подходящий подкаталог `Source/Scripts/`. Новые каталоги и пространства имён должны отражать назначение, а не конкретную сцену, если код можно переиспользовать.
- Сохраняй принятую схему пространств имён: `Source.Scripts.<Feature>`.
- Общие ассеты размещай в соответствующих каталогах `Source/` (`Prefabs`, `Materials`, `Sounds`, `Textures and Sprites` и т. п.). Не складывай рабочие файлы в `TEMP`.
- Сторонний и импортированный код в `Plugins/`, `SerializeInterfaces/`, `TextMesh Pro/`, `TutorialInfo/` и `Packages/` не редактируй без явной необходимости. Предпочитай адаптер или расширение в `Source/`.
- Не редактируй вручную сгенерированные файлы, включая `Source/Scripts/Input/InputActions.cs`. Меняй исходный `.inputactions` и регенерируй C#-обёртку средствами Unity.
- Не перемещай и не переименовывай ассеты без необходимости: ссылки Unity зависят от GUID.

## Git workflow

- `main` принадлежит пользователю. Не создавай в ней коммиты, не выполняй push, merge, rebase или force push без прямого запроса пользователя.
- `AiVersion` — основная интеграционная ветка агента и целевая ветка по умолчанию для его pull requests. Слияние `AiVersion` в `main` выполняет пользователь.
- Перед первой правкой в каждой задаче, изменяющей файлы, проверь текущую ветку и `git status`. Запомни текущую ветку как базовую и создай от неё отдельную ветку `codex/<short-task-name>`.
- Если задача уже выполняется в созданной для неё task-ветке, продолжай использовать её и не создавай вложенную ветку для уточнений той же задачи.
- Не смешивай изменения задачи с незакоммиченными изменениями пользователя. Не перезаписывай, не откатывай и не добавляй их в коммит; при невозможности безопасной изоляции остановись и сообщи о конфликте.
- После доступной проверки создай один или несколько небольших тематических коммитов, содержащих только файлы текущей задачи.
- По завершении отправь task-ветку в `origin` и открой pull request в исходную базовую ветку. По умолчанию это `AiVersion`.
- Не сливай созданный pull request и не удаляй ветки без прямого запроса пользователя.
- Задача с изменением файлов считается переданной на проверку, когда pull request создан. Если push или создание PR невозможны из-за авторизации либо недоступного инструмента, явно сообщи об этом как о незавершённом шаге.
- В итоговом отчёте укажи базовую и task-ветку, коммиты, выполненные проверки, ссылку на PR и оставшиеся незакоммиченные изменения.

## Правила кода

- Перед созданием или изменением C#-кода прочитай и соблюдай `Rules/CODE_STYLE.md`.

## Архитектура

- Для обязательных зависимостей предпочитай конструктор или Zenject-инъекцию. `FindObjectOfType`, глобальные синглтоны и service locator используй только при обоснованной необходимости.
- Регистрацию нового сервиса добавляй в installer соответствующего жизненного цикла: `Boot`, `Global`, `Menu` или `Game`. Интерфейс используй там, где он действительно задаёт границу или упрощает тестирование.
- `MonoBehaviour` отвечает за Unity lifecycle и связи с инспектором; независимую бизнес-логику держи в обычных C#-классах.
- Отписывайся от событий и реактивных подписок, останавливай tween/coroutine и освобождай ресурсы в симметричном lifecycle-методе.
- Не создавай мусор в частых `Update`/physics/UI циклах без необходимости. Используй существующие пулы для повторно создаваемых объектов.
- Сохраняй обратную совместимость сериализованных полей. При переименовании поля используй `FormerlySerializedAs` и проверяй затронутые prefab/scene-ассеты.
- Не меняй существующие написания идентификаторов и имён сцен (включая `BootsTrap`) в рамках несвязанной правки.

## Unity-ассеты

- Каждый новый или перемещённый Unity-ассет должен иметь соответствующий `.meta`; не копируй GUID между ассетами и не меняй существующий GUID.
- Сохраняй текстовую сериализацию Unity и видимые `.meta`-файлы. Не коммить `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/`, сгенерированные `.sln` и `.csproj`.
- Сцены, prefabs, ScriptableObjects, материалы и настройки изменяй точечно. Не допускай массовой перезаписи YAML или reimport-шума, не относящегося к задаче.
- После изменения сериализованных ссылок проверь отсутствие `Missing Script`, потерянных prefab overrides и незаполненных обязательных полей.
- Новые runtime-ассеты не помещай в `Resources`, если загрузка через `Resources.Load` не является осознанной частью решения.

## Проверка

- Источник истины для компиляции — Unity Editor, а не сгенерированные `.csproj`.
- Перед завершением проверь консоль Unity на compile errors и предупреждения, вызванные изменением.
- Для runtime-изменений запусти затронутый путь в Play Mode. Для загрузки и DI проверь цепочку `BootsTrap -> Menu -> Game` либо минимальный набор затронутых сцен.
- Если добавлены тесты, помещай Edit Mode и Play Mode тесты в отдельные test assemblies и запускай подходящий набор через Unity Test Framework.
- При наличии пути к редактору batch-проверку можно выполнить из корня проекта:

```powershell
& $env:UNITY_EDITOR -batchmode -nographics -quit -projectPath . -logFile -
& $env:UNITY_EDITOR -batchmode -nographics -projectPath . -runTests -testPlatform EditMode -testResults TestResults/EditMode.xml -logFile -
```

- Не утверждай, что проект проверен в Unity, если была выполнена только статическая проверка файлов. В итоговом отчёте кратко укажи, что именно запускалось и что осталось проверить вручную.

## Границы задачи

- Делай минимальное связное изменение и не рефактори соседний код без необходимости.
- Не изменяй настройки проекта, список пакетов, build profiles, сцены или prefabs, если задача этого не требует.
- Не перезаписывай пользовательские изменения. Перед правкой проверь контекст файла и после правки просмотри diff на случай случайного YAML- или форматирующего шума.
